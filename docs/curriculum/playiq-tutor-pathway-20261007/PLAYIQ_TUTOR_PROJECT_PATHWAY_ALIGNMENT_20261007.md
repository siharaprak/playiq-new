# PlayIQ Course-Long Tutor Project Pathway

**Status:** Approved course direction, source alignment revision dated 2026-10-07
**Audience:** PlayIQ curriculum, beta, and site-implementation teams
**Scope:** PlayIQ teen Course 1 only. This does not change the separate, age-neutral Sienvi course.

## The course promise

The student begins one parent-approved, private Tutor Project in Module 0 and
keeps developing that same project throughout the course. Each module supplies
one small, student-approved piece of evidence or one tested instruction. The
course teaches the student what is being built as they build it. Module 9
integrates and stress-tests the Tutor Project; it does not start a second one.
After the Tutor and the course work are complete, the student builds a separate
Personal Assistant for themselves as the final major build in the Capstone.

Keep these three builds distinct:

1. **Student Tutor Project:** one continuous project for helping this student
   learn, started in Module 0 and refined through Module 9 and the Capstone.
2. **Assistant for another person:** the user-centered design exercise in
   Module 10. It is not the student's Tutor and must not contribute another
   person's private information to the student's Tutor files.
3. **Student's Personal Assistant:** a separate, student-owned assistant built
   at the end of the Capstone, after the Tutor is finalized and tested.

## Student workflow

1. A parent or guardian selects the approved AI account, privacy settings, and
   a persistent private Project/workspace (or the closest supported equivalent).
2. The student completes Module 0's Orion assessment and creates the Tutor
   Project before beginning the student-facing Orion opening/tutorial.
3. At the end of each module, the student takes the module's assessment result
   to the same Tutor Project and asks Orion to record it using the course
   recordkeeping instructions. Orion summarizes and proposes a small update;
   the student checks it and chooses whether to approve it.
4. A result is not automatically a permanent personal rule. Preserve whether it
   is `student_reported`, `observed`, `experiment_result`, or
   `pending_validation`; keep the date, source module, and review condition.
5. Module 7 teaches Knowledge Files and produces the first topic Study Pack
   that the student may choose to add to the same Tutor Project. Before Module
   7, course evidence is a profile/rule/learning-record update, not an
   unexplained upload task.
6. Module 9 reviews the accumulated evidence, separates Project Instructions
   from Knowledge Files, integrates the approved files into the existing
   Project, and tests the result. If the original workspace was not retained,
   stop for parent-supported recovery; do not silently create a duplicate.
7. The Capstone completes final Tutor regression/consolidation first, then
   builds the student's own Personal Assistant in a separate project/workspace.
   The parent reviews both projects and the student's evidence.

## One compact record, not a new file for every module

Maintain a small, student-readable set of artifacts in the same Tutor Project:

- `Project Instructions` — role, safe teaching behaviors, and approved rules;
- `Student Tutor Profile` — goals and learning observations, with provenance
  and uncertainty visible;
- `Course Learning Record` — one concise dated entry per completed module;
- `Learning Rules` — only rules the student approves, including evidence and
  when to retest;
- `Study Packs` — source-aware topic files introduced in Module 7 onward;
- `Tutor Test and Revision Log` — observed behavior, student ratings, and
  approved changes.

Do not duplicate a module's complete workbook, scores, or private school
records in the Project. Collect only what helps the student learn and what the
student/parent approves. Never infer a clinical diagnosis or fixed learning
type. No passwords, payment details, home addresses, private family messages,
or another person's private information.

## Module-by-module Tutor Project checkpoints

| Course point | Add or test in the same Tutor Project | Evidence rule |
|---|---|---|
| Module 0 | Create the project, add starter instructions and baseline profile, record rescue/advance goals and initial assessment | Starting hypotheses only; do not claim a proven learning style |
| Module 1 | Compare the Module 0 hypothesis against the explanation/hint experiment; add one proposed explanation-start rule | One topic is a first test, not high-confidence proof |
| Module 2 | Add student-approved integrity, voice-protection, and focus/pacing settings | Distinguish a preference from a safety boundary; keep the student the author |
| Module 3 | Record pre-learning sequence and the class follow-up result | Preserve what was tested and what remains uncertain |
| Module 4 | Record the observed confusion gap and first helpful rescue move | Retest on another topic before generalizing |
| Module 5 | Record compression/retrieval comparisons and correction behavior | Do not convert one score into a memory/learning label |
| Module 6 | Record quiz/repair format, confidence calibration, and one review plan | Keep demonstrated performance separate from confidence |
| Module 7 | Create a source-aware Study Pack, test retrieval against it, and add only the approved file | Identify source, topic, date/scope, limits, and student approval |
| Module 8 | Record writing-coach preferences and authorship boundaries | Use only student-authored samples the student explicitly approves |
| Module 9 | Integrate, review, test, and revise the existing Tutor Project | No duplicate project; student applies approved changes |
| Module 10 | Build an assistant for another person as a separate design exercise | Do not import that person's private information into the Tutor |
| Capstone | Finish Tutor review first; then build the student's own Personal Assistant in a separate project | This is the final major build; keep it separate from both Tutor and Module 10 |

## Orion's course-recordkeeping behavior

The instructions installed in Module 0 teach Orion to:

1. accept one module assessment at a time and identify its module/source;
2. ask only necessary clarification questions, one at a time;
3. separate the student's report, observed activity result, checked source, and
   proposed interpretation;
4. draft one concise record and show the proposed destination and exact change;
5. mark uncertain claims `pending_validation` and avoid fixed learning-style
   labels, invented scores, diagnoses, and unsupported generalizations;
6. wait for the student's approval; never claim an external file was saved or
   uploaded unless the student confirms the action;
7. retain only information safe and useful for the Tutor Project, and flag
   parent approval when needed;
8. at Module 9/Capstone, compile only approved evidence into separate,
   human-readable Project Instructions and Knowledge Files, with a change
   summary and missing-input list before the student applies them.

## Course-site action wording for Iris

Use **Continue to Orion's Assessment** as the clear action label. Remove the
unexplained phrase “My workspace is ready.” The course must say what happens
next: the student signs into the parent-approved AI account, opens the same
Tutor Project made in Module 0, and pastes the provided assessment prompt or
answers there. If the site has no verified direct connection to the student's
external AI account, the button must display the copyable prompt and explicit
steps; it must not imply that the site can see, open, or save into the external
Project.

The parent setup happens before the student-facing Orion opening. Module 0
may then remind the student to review the parent setup together and return to
the same Tutor Project for each subsequent module.

## Acceptance checks

- Modules 0–8 point to one persistent Tutor Project and provide a clear
  student-approved update step.
- Module 0 calls initial preferences hypotheses/baselines, not permanent or
  proven traits, and teaches Orion's course-long recordkeeping behavior.
- Module 7 is the first formal Study Pack/Knowledge File build and explains
  source, purpose, limits, and safe use.
- Module 8 describes the last pre-integration update, not the beginning of the
  Tutor Project.
- Module 9 integrates/tests the project made in Module 0; no duplicate parent
  setup or new-project requirement.
- Module 10 remains an assistant for another real user and stays separate.
- The Capstone's last major build is the student's own Personal Assistant,
  separate from the Tutor and Module 10 assistant.
- Beta feedback, where present, remains beta-only and at the end of its module.
- No site code, deployment, or external service wiring is implied by this
  curriculum revision.
